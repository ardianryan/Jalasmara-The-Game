# Public PCK readiness and moodboard gap, 15 November 2026

The owner asked to reduce first-load trouble and requires **full** visual parity with the supplied cozy pixel-art moodboard. The currently released game is **not** at that visual standard. This package improves release readiness checks; it does not alter the game renderer or claim a finished art pass.

## Public transfer diagnosis and change

The two cold Chromium/H2 traces for PCK `e317a3bc9195` reached only 44–49% in the 120-second game-startup limit. Their completed 1 MiB PCK requests took a median 19.1–19.5 seconds each, while TTFB medians were 0.6–2.9 seconds. The same staging build after a six-client public warm-up served completed parts to Chromium in a median 0.11 seconds and passed the six public smoke checks. A later single H2 probe varied between 0.11 and 5.19 seconds. These observations point to a variable public transfer/cache path, but do **not** isolate the proxy, provider, or individual device network as the cause.

`scripts/prewarm-public-pck.mjs` now performs a bounded, six-socket public read of every PCK segment after a new release is active. It pins the expected full PCK SHA, checks the public manifest, exact byte count and offset of each part, and verifies every part's SHA-256. It permits one retry per part, aborts per-part after 60 seconds and the whole run after five minutes, and rejects oversized responses. This does not change the in-game four-request loader, its visible byte progress, the proxy, or the game bundle. The release runbook places this verification after health/hash activation and before the fixture-backed smoke, while requiring any separate cold-start measurement to be reported before warm-up.

The first CLI implementation used Node's default fetch transport and had not completed after roughly three minutes; it was interrupted. Replacing the CLI transport with six explicit keep-alive HTTPS sockets verified **70/70 parts, 72,961,404 bytes, zero retries in 8,858 ms** on the current, already warmed staging SHA. That is a warm-path tool result, **not** proof of a new-SHA cold start or Windows/S23 loading time. The earlier Python six-client warm-up took about 27 seconds and preceded the successful browser smoke; conditions were different. The new tool has no credentials or state mutations. Three focused tests cover complete verification, stale manifest rejection and corrupt-part rejection; CI includes them. Tooling: Node 22 built-ins `https` and `crypto`, no new dependency or asset/license change.

## Visual acceptance ledger

Compare the [released dock screenshot](../visual/pixel-refinement-staging-ready-20261115.png) and [native reef screenshot](../visual/ocean-pixel-refinement-20261115.png) with the owner's supplied moodboard at actual 844×390 and 667×375 gameplay sizes. The moodboard images remain references only and are not copied into the repository.

| Area | Current evidence | Gap to full parity and acceptance |
| --- | --- | --- |
| Pixel clarity | Nearest-neighbor world and smaller swim palette are active. | Character, building, terrain and reef assets have visibly different pixel-cluster density. No soft source-edge or noisy speck should survive at game size. All 8 directions/poses need moving-frame review, not only a still. |
| Coastal world | Warm wood, teal water and nonrectangular shore are present. | The dock view has broad flat deck/water/grass regions and much less authored set dressing, shadow hierarchy and architectural detail than the moodboard. Add purposeful local props and material clusters without blocking paths/HUD or changing server walkability. |
| Underwater world | Three parallax relief layers, fish, coral and equipment are visible. | Large midwater regions remain flat; reef/rock silhouettes and near/mid/far contrast lack the moodboard's scene composition. Add depth and controlled detail while keeping targets readable and FPS stable. |
| Lighting/color | Cheerful daylight and cooler teal sea are present. | Scene-specific warm highlights, cool colored shadows and readable dusk/night contrast need matched captures. Raising global saturation alone cannot meet this gate. |
| UI and characters | Bahari HUD and modular gear exist. | At 667×375 the HUD must leave play space clear; icons, dialogue portraits and world sprites need one consistent art direction. Face, gait, swim, recoil and damage must be checked as animation on Windows and S23. |

**Next work order:** (1) acquire same-camera/daylight and night/reef comparison captures, (2) repair source art and cluster density for Nala/residents/architecture at runtime scale, (3) fill coastal and underwater composition with intentional limited-budget detail, (4) tune lighting and HUD against those scenes, (5) test moving gameplay and load/frame pacing on Windows and Samsung S23. Do not mark any row accepted from this ledger alone. Each visual package needs source/provenance/license, native render, browser screenshots, performance comparison, and owner review.
