# Hub V junction: root cause and implementation handoff

**Status: diagnosis only.** This audit starts from `7e3f1c94538756141f974ca954e9601be895a3ad` on `work/route-root-cause-audit-20261118`. It changes no runtime, asset, walkable floor, collision, route, stair, or material. No native or browser render was run for this audit. The current warm packed-earth path remains the accepted baseline.

## Source of the shape

The hub route graph in `packages/shared/src/land.ts` has a lower-court spine `(600,950) → (1120,1000) → (1370,950) → (1600,950)`, a dock spur `(1120,1125) → (1120,1000)`, and a central-stair spur `(1370,950) → (1370,815)`. The latter meets the east-west path at a right angle. The 3/4 camera projects that T branch as the conspicuous V/Y near the central stairs. The small bend at `(1120,1000)` adds another visible cusp. These routes are gameplay/navigation data and should remain unchanged.

`packages/shared/src/village-ground.ts` then paints **each** route segment as an independent 72-unit-wide quadrilateral and **each** vertex as an octagon. It clips every piece separately to each court and subtracts stone, wood, dock, bridge, and garden footprints. A remainder over only one square world unit survives. This creates the detached scratches around thresholds; it cannot compose one continuous path edge. In `client-godot/scripts/land/LandWorld3D.gd`, each surviving nonwalkable dirt polygon gets its own seven-unit inset and feathered edge. The lower court's outer coastline contour is naturalized, but the internal path is not. CPU walkability tests pass because all these dirt surfaces have `walkable: false`; they cannot determine whether the projected junction looks good.

The [court-mask](land-route-court-mask-diagnostic-2026-11-18.md), [authored-footprint](land-route-authored-court-diagnostic-2026-11-18.md), [convex-patch](route-composition-diagnostic-2026-11-18.md), and [integrated-shader](route-integrated-court-diagnostic-2026-11-18.md) trials changed masks, width, tint, or feathering while retaining a continuous dirt branch at `(1370,950)`. Actual-size renders showed either the same V, disconnected slivers, or a broad apron. More uniform corridor or local circular wear is not a useful next trial.

## Bounded implementation candidate

Treat the lower court's **central stair approach as a different surface treatment**, so the dirt spine does not form a continuous V with it. Keep the accepted dirt material and 72-unit visual width on the main spine. Stop the central **dirt** branch at the existing horizontal path's north edge, about `y=914` at `x=1370`; from the existing stone stair toe `(1370,815)` to `(1370,914)`, place a short sequence of grounded, irregular stone treads in the same 72-unit-wide approach corridor, with narrow grass joints. The last tread should visually meet the path edge without a large dirt or stone landing. Candidate tread centers are `(1370,838)`, `(1370,862)`, `(1370,886)`, and `(1370,908)`; each stays within `x=1334…1406`, is roughly 16–20 units deep, and has softened nonrectangular corners. These are **visual** surfaces at lower-court height, not new walkable floors or raised collision. Match their tone and scale to the existing central stone stairs; avoid a bright continuous band. Keep the west stair approach and dock transition outside the first patch, then inspect them separately.

For the lower dirt spine itself, replace per-segment quads/octagons with **one explicitly joined strip mesh** spanning `(600,950) → (1120,1000) → (1370,950) → (1600,950)`. Use a bounded curved join at `(1120,1000)` with control points inside a 30-unit radius of that vertex; hold a minimum 72-unit visible width along the intended walking line, but no bulge wider than 88 units. The visual-only centerline may deviate by at most 12 units from the original polyline, so its alignment with the unchanged floor remains legible. Give this single strip one outside feather rather than one feather per old polygon. Do **not** place an octagonal pad at `(1370,950)`: the spine passes through, while stone treads approach it from the north. At the east-west/dock branch, retain the baseline initially; if the first patch is accepted, apply the same explicit-junction method in a separate small trial. Do not alter the upper court in this patch.

Suggested ownership: `packages/shared/src/village-ground.ts` for the hub's visual-only path specification and exclusion of just the central dirt spur; one new Godot helper such as `client-godot/scripts/land/HubCourtPath3D.gd` for the joined visual strip/tread geometry; and a narrow call in `client-godot/scripts/land/LandWorld3D.gd`. Reuse existing materials from `LandMaterials.gd`. Keep `packages/shared/src/land.ts`, the server floor union, `ground_height`, the three stairs, connector geometry, and the route graph read-only. Avoid a whole-court shader field or another collection of overlapping clipped polygons. If a single joined strip cannot fit cleanly against protected surfaces, reject the candidate rather than expanding it into a broad apron.

## Acceptance gate for the later implementation

1. CPU: compare the authoritative hub floors, routes, stairs, connector IDs, height samples, and a fixed 2,000-point walkability sample to baseline; they must be identical. Measure the visual spine's centerline deviation ≤12 units, width 72–88 units, and simple, non-self-intersecting output. Confirm four treads stay in `x=1334…1406`, `y=815…920`, remain at lower-court height, do not overlap the stair's protected floor, and emit no fragment smaller than 500 square world units. The visual surfaces must be `walkable: false` and excluded from collider construction.
2. Native original-size A/B at the same hub camera poses, **667×375 and 844×390**: the lower path remains easy to follow; the central stair reads as connected stone treads rather than a dirt V; no broad orange/brown slab, pale scratches, sharp right-angle band, floating stone, or grass seam is visible. Inspect moving traversal through `(1120,1000)`, `(1370,950)`, and `(1370,815)`, not just a still. Keep the accepted warm packed-earth/grass balance.
3. If that passes, run Godot import and error-log scan, `npm run check:world`, `npm run typecheck`, `npm test`, and `npm run build`, then browser motion and performance comparison before staging. A CPU pass or renderer fixture alone is not acceptance.

**Handoff:** This is a proposed small visual-only implementation, not a validated fix. The next owner should take the files above in an isolated worktree, capture matched actual-size A/B, and reject the patch if the V still dominates. Tools used in this audit: source inspection with `rg`, `sed`, and `git`; no external tools, assets, licenses, or renderer slot were used.
