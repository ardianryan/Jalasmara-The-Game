# Profiling override with segmented PCK delivery

The rendering profiler's `PROFILE_OVERRIDE_PCK` route only replaces same-origin GET `/game/index.pck`. Current exports fetch a manifest and versioned parts instead. Installing the old route could therefore load the served candidate before eventually failing its interception assertion; it cannot truthfully profile an alternate PCK through the segmented loader.

A new local-only preflight runs before report creation, Mongo/Redis connection, fixture insertion, or browser launch. An override is allowed only when `/game/pck-manifest.json` actually returns404. Any present manifest fails with an explicit unsupported-segmented-delivery message; other HTTP statuses and network errors fail closed. It does not modify the production loader, manifest, bootstrap or part routes. Served profiling does not issue this override probe. The existing exact direct-route interception count still verifies delivery for supported legacy controls, and intercepted startup measurements remain excluded.

CPU proof: `node --test scripts/performance/pck-source.test.mjs` passed7/7. This covers actual selected-file hash provenance, exact same-origin request matching, no probe in served mode, a bounded same-origin404 probe, rejection of a present manifest, rejection of204/redirect/auth/server/network failures, and rejection of non-local targets before a request. `node --check scripts/performance/browser-baseline.mjs` and `git diff --check` passed. No engine, browser, database mutation or new benchmark was run.

To measure the current segmented candidate, run the existing served mode with `PROFILE_PCK_FILE` pointing to the exact built candidate and verify its delivery/package independently. Alternate-file A/B rendering controls remain unsupported for segmented exports until an explicitly reviewed whole manifest/bootstrap/part override is implemented. Historical direct-PCK comparisons retain their original package and delivery scope; they are not relabeled as tests of the new segmented path.
